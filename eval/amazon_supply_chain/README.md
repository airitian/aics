# Amazon 供应链标准手册 · AI 客服准确率测试

用一份真实的外部文档（亚马逊《供应链标准手册》简化中文版，13 页）当知识源，
对 AICS 的 AI 客服做一次可重复的准确率评测。

## 文件清单

| 文件 | 用途 |
| --- | --- |
| `questions.json` | **题库唯一数据源**（86 题，含标准答案、出处、判分规则） |
| `amazon供应链标准手册_测试题库.md` | 人读版题库 —— 想手工测就照着念 |
| `amazon供应链标准手册_测试题库.csv` | 可导入 Excel / 测试管理工具（UTF-8 BOM，双击不乱码） |
| `export_questions.py` | 从 `questions.json` 重新生成上面两个文件 |
| `run_accuracy_eval.py` | 自动跑评测、判分、出报告 |
| `diagnose_recall.py` | 单题排查：为什么这题答不上来（召回排名 + 结论） |
| `reports/` | 历次评测的报告（Markdown）与原始数据（JSON） |

## 怎么用

```bash
cd aics/eval/amazon_supply_chain
PY=C:\Users\Administrator\.workbuddy\binaries\python\envs\default\Scripts\python.exe

# 1) 全量跑（约 5 分钟 / 86 题）。需先启动服务
$PY run_accuracy_eval.py

# 2) 只跑某一类，例如防编造题
$PY run_accuracy_eval.py --category H

# 3) 改了判分口径后「只重判分、不重新提问」—— 不烧 API
$PY run_accuracy_eval.py --rescore reports/eval_result_20260923-013532.json

# 4) 重新导出人读版题库
$PY export_questions.py

# 5) 单题排查：这题为什么答不上来？
$PY diagnose_recall.py A10
$PY diagnose_recall.py --question "审完要交什么东西？" --top-k 30
```

`diagnose_recall.py` 会把题目判分用的关键词直接当探针，告诉你答案块排第几名，
并按「top_k 不够 / 被 MIN_SCORE 砍掉 / 检索没覆盖 / 模型没用上」四种情况给出结论 ——
它是把失败题归因到具体环节的入口，比反复改参数试要快得多。

走的是系统内置的**问答测试（Playground）**链路：不产生线上会话、不落工单，可以放心反复跑。
退出码 0 = 全通过，非 0 = 有未通过项，可直接挂到定时任务上。

环境变量可覆盖默认值：`AICS_BASE`（默认 `http://127.0.0.1:8000`）、
`AICS_EVAL_EMAIL` / `AICS_EVAL_PASSWORD`（默认演示租户 `star@demo.local`）、`AICS_EVAL_EMPLOYEE`。

## 题库结构（86 题 / 9 类）

| 分类 | 考什么 | 题数 |
| --- | --- | --- |
| A 单点事实 | 文档里一句话就能答，考「找得到」 | 14 |
| B 数值与期限 | 记不准就会答错，最容易糊弄过去 | 14 |
| C 清单枚举 | 考「漏不漏」 | 10 |
| D 条件组合 | 需要把两处以上信息拼起来 | 10 |
| E 否定与陷阱 | 文档写了「不接受 / 不意味着」，答反即高危 | 8 |
| F 边界与例外 | 只在特定国家、特定情形成立 | 7 |
| G 口语化换问法 | 用供应商真实口吻问，考检索鲁棒性 | 8 |
| H 文档外问题 | 手册里根本没有，正确行为是承认没有 | 9 |
| I 行为验证 | 转人工 / 拦截策略（非文档知识） | 6 |

判分是关键词命中式，属**下限判定**：判过的不代表表述完美，判不过的一律附上 AI 原文供人复核。
容易误伤的编造类检查放在 `review_if`（软标记，只提示复核不判失败），而不是 `must_not`。

## 未通过的 7 题与根因（都有实测数据支撑）

### 1. 口语化提问召回下降 —— G 类只有 50%（主因）

同一知识点的正式问法 vs 口语问法，答案片段在检索里的排名：

| 知识点 | 正式问法排名 | 口语问法排名 |
| --- | --- | --- |
| 审计时长 | 第 2 名 | **第 3 名** |
| 生产外包 | 第 1 名 | 第 12 名 |
| 环保措施 | 第 1 名 | 第 7 名 |
| CAP 提交时限 | 未进 top20 | 未进 top20 |

**唯一变量是问法**，说明不是知识库缺内容，而是「短口语问句 vs 600 字多主题块」的相似度整体被压低。
`TOP_K=5` 不够用 —— 第 7、12 名的答案块被挡在上下文之外，模型于是诚实地说「没查到」。

> 注意：这几题模型都**没有编造**（H 类 9/9 通过），只是答不上来。安全性没问题，可用性有损失。

**建议**：接 `bge-reranker-v2-m3` 做两阶段召回（粗排 top20–30 → 精排取 5）。
该接口此前已验证可用但未接入。单纯把 `TOP_K` 调大会引入噪音并推高 prompt 成本。

### 2. 密集列表被稀释 —— A10 直接 0 命中

「谁被称为工厂的主要权利持有人」的 top20 相似度全部落在 **0.4369 ~ 0.329**，
**无一过 `MIN_SCORE=0.45`**，于是 0 命中走了兜底。但正确答案就在**第 4 名**（0.4052）那块里。

根因是术语表这种「一条一义」的密集列表被揉进同一个 600 字块，
单条查询的相似度被十几条定义稀释 —— 与之前「6 条 FAQ 并在一个块」是同一类问题，
当时靠 `min_fill = CHUNK_SIZE//3` 解决，但术语表这类内容仍然会整块成形。

### 3. 清单被切分截断 —— C10 只答出「四大类」

附录 7 的清单有 7 大类，实测 top1 片段长 **597 字**（正好撞上 `CHUNK_SIZE=600`），
恰好在「薪资/考勤文件」之后被切断，于是它只包含前 4 类的**小标题**：

```
商务文件 / 工厂政策和程序 / 员工文档 / 薪资/考勤文件   ← top1 就到这里结束
```

其余 3 类里，「结社自由、健康和安全、环境」只作为「工厂政策和程序」那行政策枚举中的**词**出现，
而不是独立小标题；「健康与安全/环境」的独立小标题落在第 3 名那块。

模型读到的是一个结构完整的「四大类」列表，于是照实答了四大类 ——
**模型是诚实的，是切分把清单切断了。**

**建议（第 2、3 条）**：对「术语表 / 附件清单」这类结构化内容按条目或小节切分，
不要按字数硬切。这属于入库策略，改完需要重新入库。

### 4. E05 答得不全

模型答出「孟加拉国、柬埔寨、印尼」，漏了埃塞俄比亚与海地，
且把「工厂服务套餐覆盖国」与「必须参加的国家」混在一起 —— 属模型归纳能力问题，非检索问题。

## 顺带修掉的一个真 bug

评测暴露出「问答测试」功能本身是坏的：任何走到**追问澄清**分支的问题都会崩。

- `clarify_count` / `no_answer_streak` 的默认值由数据库在 **INSERT 时**填，
- 而 Playground 刻意复用「不落库的探针 Session」，读出来是 `None`，
- 于是 `None += 1` 与 `None < int` 直接抛 `TypeError`。

偏偏「无意义输入」和「低置信 + 追问澄清」正是问答测试最该覆盖的场景。
修法是不假设对象已落库（`app/agent.py` 的 `_counter()`），
并在 `tests/test_flows.py` 补了两条回归用例。测试总数 135 项，全绿。

## 判分口径的已知局限

1. **关键词命中是下限判定**：答对了但用词完全不同的情况会被判失败。
   已把「查不到」类表述改成**正则**匹配（模型会把兜底话说进自己的句子里，
   如「暂时没有亚马逊供应商账号和密码的**相关资料**」，字面匹配会漏）。
2. **模型输出有随机性**：同一套题两次跑结果会有小幅波动，
   单题失败不必立刻当成 bug，先看 `reports/` 里前后两次的差异。
3. **`_recall_diag*.py` 式的关键词定位**用于人工诊断，
   needle 词在切分处被拆开时会假报「未出现」（B01 对照组就是这样），结论要看原始片段。
